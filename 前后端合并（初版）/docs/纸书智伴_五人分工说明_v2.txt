“纸书智伴”五人分工说明（v2）

修订日期：2026年11月9日
修订依据：v1 分工说明；赛题规则《“纸书智伴”—纸质图书多模态智能升级与智能伴读》；参考代码 tts_book 与演示视频。
本版主要变化：
  1. 补齐 v1 中无人负责的工作：视频生成、ASR/TTS、视频内检索、延迟优化、多 Agent 编排、儿童内容安全、官方评测接口对接、多模态对话历史、演示视频与答辩材料。
  2. 减轻 B 的负担：故事生成与视频生成链路移交 A；B 专注“内容理解 + 检索问答 + 触控识别”。
  3. 协作方式由串行改为并行：第一周先定数据与接口格式，用假数据让五人同时开工。
  4. 每人标明对应的评分维度，工作优先级以评分为准。


零、全员共同约定（第一周内完成，五人一起参与）

1. 统一分页数据（由 B 起草，全员确认后冻结为 v1.0，之后修改须通知全员）：
   book_id、page_no、page_image、ocr_text（含文字框坐标）、narration（朗读旁白）、characters（人物及外观设定）、objects（名称、坐标框、简短讲解）、scene_summary、plot_events、video_clip_id、time_range、keyframes（关键帧时间、画面描述、物体框）、source_reference、safety_check（审核结果、年龄适配标注）。
2. 统一接口约定（由 A 起草）：每个请求带 book_id、page_no；视频相关请求另带 play_time（当前播放秒数）；每个响应包含 status、data、error、run_id、耗时。
3. 统一运行记录：每次生成都写入 logs/，记录 run_id、时间、输入、提示词版本、模型名称及参数、输出文件路径，保证“任何一个生成结果都能找到它是怎么来的”。
4. 样本合规：官方绘本到手前，只使用 AI 生成或队员自己绘制的“模拟绘本”开发，不使用购买或网上下载的绘本拍照、扫描件（赛题禁止）。
5. 密钥只放环境变量，不进代码、不进文档、不进仓库。
6. 所有代码、提示词、配置、测试题、素材放在同一个版本仓库，按目录分工：
   configs/  agents/  web/  eval/  logs/  docs/  data/（受限数据不入公开仓库）


一、A｜后端、生成链路与系统集成（有基础）

对应评分：绘本生成质量（生成效率）、交互延迟、多 Agent 协同（实现）、系统可运行门槛。

工作目标：搭好能稳定运行的服务，并负责“故事 → 配音 → 视频”这条生成链路和语音链路，把交互延迟压到门槛以下。

具体落实步骤：
1. 摸清现有后端：检查 story_tts_server.py 的路由、config.py、依赖与启动方式；列出接口清单，逐项做最小调用测试，标明“已跑通 / 依赖外部 API 待验证 / 不可用”，并记录费用和单次耗时。
2. 先写“假接口”：按共同约定返回固定示例数据，让 C 第一周就能联调页面、D 能搭测试脚本，不必等真实模块。
3. 补齐通用功能：上传文件校验、异步任务队列与状态查询、异常处理与重试、日志（按零.3 的格式）、配置管理。
4. 故事生成：以 B 给出的分页数据为依据，把 OCR 原文改写成适合儿童朗读的逐页旁白（是“改写与讲述原书”，不是另编新故事），保持人物称呼和情节一致；复用参考代码的故事模块并改提示词。
5. 视频生成：
   - 以原绘本页插图作为图生视频的首帧，保证画风与原书一致；
   - 使用 B 的人物设定和前后页摘要组织提示词，保证跨页连贯；
   - 用 MoviePy 完成片段拼接、配音、字幕与转场；
   - 生成时把每个片段的页码、time_range、旁白、提示词写回分页数据，供 B 建检索索引；
   - 记录每次调用费用，按预算控制调试次数。
6. 语音链路：接入 ASR（参考代码现有服务或 FunASR）和 TTS（现有服务或 CosyVoice），比较识别准确率与延迟后选定方案。
7. 延迟优化：流式 ASR；大模型流式输出，首句一出即送 TTS；触控结果预计算查表；常用连接保持；分段记录 ASR、检索、回答、TTS 各环节耗时，以“说完话到听到第一个字”的首响时间为主指标。
8. 编排实现：按 B 设计的节点图，把 OCR、VLM、故事、视频、检索、安全复核各节点接成可编排链路（先用普通 Python 函数串联，稳定后再考虑 LangGraph），每个节点有输入、输出、失败重试和日志。
9. 多模态对话历史：保存每轮问答的文字、提问录音、回答音频和相关画面截图，按会话存储；交互日志中的语音/图像脱敏保存。
10. 对接官方评测接口：按命题组公布的统一输出格式实现导出与提交脚本。
11. 部署：准备一键启动脚本，在比赛提供的云 GPU 环境上验证；准备主备网络方案。

交付内容：可启动的主项目与启动说明；接口清单与调用示例；视频生成脚本与片段索引；ASR/TTS 选型对比表；分环节延迟测试记录；官方评测接口对接脚本；成功和失败的运行日志。

交接关系：给 C 稳定的接口；给 D 可重复测试的环境和批量调用脚本；从 B 接收分页数据与节点设计；向 E 提供日志与运行证据。


二、B｜内容理解、检索问答与触控识别（有基础）

对应评分：回答正确性（语音问答、视频内检索）、触控式万物识别、绘本生成质量（图文内容准确度）、多 Agent 协同（设计）。

工作目标：把每页绘本和每段生成视频变成结构化、可检索的数据，并用它支撑问答和触控识别。

具体落实步骤：
1. 起草统一分页数据格式（见零.1），并先手工做 2—3 页示例数据交给全员，作为假数据开工的基础。
2. 逐页提取：PaddleOCR 提取文字及位置；视觉语言模型（如 Qwen3-VL）识别人物、物体、场景、动作，并直接输出物体坐标框；合并成一份分页数据。绘本字体特殊时，用 VLM 读文字作为 OCR 的补充对照。
3. 人物设定表与跨页事件表：整理每个人物的外观、称呼、性格，以及按页顺序的事件，交给 A 用于故事和视频生成。
4. 人工核对：每本书抽查若干页，核对漏字、认错人物和物体、描述与原图不符的情况，据此调整提示词，并记录调整前后的效果。
5. 视频内检索：
   - 对 A 生成的每个视频片段抽取关键帧，用 VLM 写画面描述并标出物体框；
   - 建立“页面 + 视频片段 + 时间段”的混合索引（关键词 + 向量）；
   - 回答时只依据检索到的内容作答，同时返回页码和时间戳，前端可直接跳转播放；
   - 检索不到依据时如实回答“书里没有提到”，不编造。
6. 触控识别：
   - 主方案：入库时预先计算每页和每个关键帧的物体框，触控时按坐标查表，返回物体名称和讲解；
   - 兜底方案：查表无结果时，以点击点为中心裁剪局部图交给 VLM 识别；
   - 视频暂停时按当前播放时间取最近的关键帧，坐标按帧映射，不能直接套用原页图的框；
   - 准确率仍不够时，再评估 Grounding DINO 或 SAM 2。
7. 多 Agent 节点设计：画出节点图（OCR、VLM 理解、故事规划、视频生成、检索问答、安全复核），定义每个节点的输入、输出和失败处理，交给 A 实现。
8. 安全复核节点：对生成的旁白和回答做敏感内容检查，附上年龄适配标注；不确定的内容标记出来，交给人工复核。
9. 依据 D 的错误分类结果持续改进，每次改动记录“改了什么、分数变化多少”。

交付内容：冻结的分页数据格式；全部绘本的分页数据；人物设定表与事件表；检索问答接口；触控识别接口；节点设计图；提示词版本记录与改进前后对比。

交接关系：向 A 提供分页数据、人物设定和节点设计；从 A 接收视频片段索引；向 D 提供可批量调用的问答与触控接口；向 E 提供方法说明素材。


三、C｜前端与交互体验（初学者）

对应评分：交互延迟（体感与稳定性）、现场演示效果、触控识别（前端部分）。

工作目标：在参考网页基础上做出适配平板的互动阅读页面，让用户顺畅完成“看绘本—看视频—提问—点击识物”。

具体落实步骤：
1. 熟悉现有网页：从 tts_v2.html 入手（演示视频里的翻书阅读、问题气泡、点击识物、语音小助手、测验均来自它），梳理页面、按钮和请求地址，列出保留、改造和新增的部分。
2. 画出操作流程：选择或上传绘本 → 翻页阅读 → 播放生成视频 → 录音提问 → 查看回答及依据（页码、视频时间点）→ 点击画面识物 → 查看对话历史。
3. 第一周就对接 A 的假接口开发，字段严格按共同约定使用，不在前端另起一套格式。
4. 完整交互状态：等待中、成功、无结果、失败都有明确提示；视频生成等长任务显示进度。
5. 录音与触控：
   - 网页负责录音采集和发送；
   - 触控时发送 book_id、page_no、点击坐标（按图片实际尺寸换算）以及视频的当前播放时间 play_time；
   - 识别结果在画面上用框和标签显示，并可朗读讲解。
6. 回答依据展示：回答附带页码和时间戳时，提供“跳到这一页 / 跳到视频这一刻”的按钮。
7. 对话历史：展示文字、可回放的提问录音和回答音频、相关画面截图。
8. 平板适配：触摸事件、横竖屏、按钮尺寸、移动端浏览器的麦克风和自动播放权限，在真实平板上测试。
9. 逐条走完整流程，记录页面异常和接口不匹配的问题，交给 A 处理；协助 E 录制演示视频与截图。

交付内容：交互流程图；可在平板上操作的网页；前后端联调记录；完整操作录屏；问题清单。

交接关系：从 A 接收接口；在 B 的识别结果基础上做展示；配合 D 做可用性测试；配合 E 录制演示视频。


四、D｜样本、题库与评测（初学者）

对应评分：为“回答正确性”“触控识别”“交互延迟”“绘本生成质量”提供自测数据；支撑“改进有依据”的说明。

工作目标：建立一套与官方评测尽量一致、可重复运行的测试体系，用分数指导每周的改进方向。

具体落实步骤：
1. 样本管理：官方样本到手前，管理团队制作的模拟绘本；官方样本到手后，为每本书、每一页编号并登记来源。受限数据只存在指定位置，不外传。
2. 标注规则：规定页面文字、人物、物体（名称和框）、情节事件、问题答案及证据页码/时间点的标注方法，多人标注时按同一规则。
3. 问答题库：每本书自建约 50 题（对齐官方每本 50 条 Query），题型覆盖页面事实、人物关系、情节因果、物体属性、视频画面细节；每题写参考答案、证据页码或视频时间点、判分标准。
4. 语音测试集：为题库录制提问音频（可由队员录制，男女声、语速、带少量环境噪声），用录音跑端到端测试，不只测文字。不采集真实儿童的语音。
5. 触控测试集：选不同大小、遮挡、位于视频不同时间点的物体，标注正确名称和位置，统计“定位正确率”和“命名正确率”。
6. 评测脚本：在 B 的指导下使用批量调用脚本，一键跑完题库并输出正确率、各环节耗时、失败列表；官方数据和评测接口下发后，第一时间跑出基线分数。
7. 每周定期测试：每周固定一次全量测试，记录版本号和分数变化，形成“基线版 vs 改进版”对比表。
8. 错误分类：分为 ASR 识别、文字识别、画面理解、检索未命中、回答错误、触控错误、接口调用、网页交互等类型，每条附复现步骤，交给对应负责人。
9. 生成质量评价：设计风格一致性、页间连贯性、图文准确度的打分表，组织队员按“盲评”方式给生成视频打分。

交付内容：样本台账；标注规则；问答题库（含语音）；触控测试集；评测脚本使用说明；每周测试结果表与对比表；错误分类与问题单；生成质量打分表。

交接关系：从 A、B 接收可批量调用的接口；向 A、B 反馈错误；向 E 提供测试数据，用于说明书第 7 章。


五、E｜质量统筹、合规、文档与演示（初学者）

对应评分：规范合规（材料完整、来源披露、儿童内容审核、年龄适配标注）；答辩与演示。

工作目标：让进度、版本、来源授权、说明书和演示内容彼此一致，并负责全部合规材料和对外展示材料。

具体落实步骤：
1. 进度与版本：维护任务表（负责人、交付物、状态、阻塞问题），记录每次测试和演示对应的代码、提示词、模型版本。
2. 来源与许可台账：分别登记代码、模型及权重、第三方 API（调用范围与额度）、绘本、音频及其他素材的来源、版本、许可链接与使用方式；不清楚的标“待确认”并跟进。按说明书模板第 4 章的表格格式整理。
3. 儿童内容安全机制：
   - 制定审核流程：自动安全节点初筛 → 人工复核 → 记录结果；
   - 推动团队指定“内容安全复核责任人”（建议由指导教师或一名队员担任），写入说明书封面；
   - 保存复核记录与年龄适配标注。
4. “预生成与现场生成”口径说明：明确哪些内容事先生成（附 run_id 和日志，可复现），哪些在现场实时生成（至少一页从上传到出视频的完整链路），答辩时如实说明，避免被认定为“用固定结果冒充现场生成”。
5. 收集证据：向 A—D 收集运行日志、截图、测试结果和失败记录；说明书只写有证据的功能，未完成或未验证的单独标注。
6. 项目说明书：按官方模板（项目说明书模板.docx）的 9 章结构撰写，建议不超过 20 页；配系统架构图、页面截图、测试表。
7. 演示视频（5 分钟以内）与答辩材料：编写分镜脚本，与 C 一起录制；准备 8 分钟答辩（5 分钟陈述 + 3 分钟问答）的 PPT 和问答准备清单。
8. 现场备用：准备本地演示视频和关键页面截图；提前检查服务、网络、账号、平板和素材。
9. 提交前核对：说明书、演示与实际版本一致；清除密钥和个人信息；代码、关键配置、素材来源清单、知识产权承诺书齐全。

交付内容：进度与版本表；来源许可台账；内容安全审核流程与复核记录；生成口径说明；说明书；演示视频；答辩 PPT；备用材料；提交检查清单。

交接关系：从 A—D 收集材料；负责统一对外的版本和口径。

七、协作节奏与里程碑（具体日期待官方公布提交时间后填写）

第 1 周：共同定好数据格式和接口；B 交付 2—3 页示例数据；A 提供假接口；C、D、E 同步开工；A 完成外部 API 可用性清单。
里程碑 1｜单页闭环：一页模拟绘本 → OCR/VLM → 旁白 → 配音 → 图生视频片段 → 文字问答，完整跑通并有日志。
里程碑 2｜整本闭环：一本书全部页面跑通；语音提问、视频内检索、触控识别可演示；D 跑出第一次全量自测分数。
里程碑 3｜官方数据接入：拿到 6 本绘本和 Query 音频后，一周内跑出官方数据的基线分数，确定重点改进项。
